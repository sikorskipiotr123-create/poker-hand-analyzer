## Key features

- **Visual hand entry:** select Hero, Villain, and board cards; duplicate-card validation prevents impossible combinations.
- **Mathematical Analysis:** evaluate hand strength and board texture, compare known hands or ranges, and inspect wins, losses, ties, equity, required equity, and call EV.
- **13×13 Range Matrix:** choose pair, suited, and offsuit classes individually or with presets. Physical combinations are generated correctly and removed when blocked by known cards.
- **Exact and estimated equity:** enumerate all legal outcomes when practical; otherwise run chunked Monte Carlo simulation. The interface identifies the method and reports the number of cases or simulations.
- **Action and stack tracking:** record street-by-street actions and positions, starting and remaining stacks, all-ins, effective stack, automatic street progression, and SPR.
- **AI Poker Analysis:** request a structured review using positions, action history, ranges, opponent profile, optional player statistics, stack state, and language.
- **Polish and English:** localized interface and AI responses. Changing the interface language does not silently submit a new AI request.
- **Demo hand:** load an example to explore the mathematical workflow.

## How it works

### Mathematical Analysis

The in-project poker evaluator ranks Hold’em hands from high card through straight flush, including kickers, ties, and the wheel straight. Range classes expand into physical card combinations: a pair has six, a suited class four, and an offsuit class twelve before blockers.

Known cards are removed from the available deck. When the complete legal outcome space is within the engine’s exact-enumeration bound, every legal runout is evaluated. Larger spaces use Monte Carlo sampling without replacement, processed in chunks to keep the interface responsive. Estimates can vary between runs.

Pot odds and EV use the following definitions:

- **Final pot after call** = current pot + Villain’s bet + Hero’s call.
- **Required equity** = Hero’s call ÷ final pot after call.
- **EV(call)** = equity × final pot after call − Hero’s call.

The recommendation follows the resulting call EV: positive supports a mathematical call, negative supports a fold, and values close to zero are approximately break-even. It does not account for future betting, rake, or opponent behavior.

### AI Poker Analysis

When the user explicitly requests a review, the browser sends the supplied hand context to a server-side Next.js route. The route validates the request, applies usage controls, and calls the OpenAI Responses API using Structured Outputs.

The server rejects incomplete provider responses and validates the returned fields before display. Mathematical context shown with the review is recomputed server-side from validated primitive assumptions, not accepted from client calculations or model-generated prose. The server enumerates equity only within its fixed budget; otherwise equity and dependent call EV are explicitly unknown. AI commentary can be incomplete or mistaken; it does not calculate equity or EV and does not promise an optimal strategy.

### Deployment security

The live application uses explicit public access, server-only provider credentials, trusted Vercel client-IP handling and shared Upstash Redis controls. Production tracks the repository's `main` branch. The [production release notes](docs/production-release.md) record the persistent non-secret configuration and the Next.js security patch.

AI review has a default **16,000-token output cap**, a shared concurrency limit of **3**, and a server-side kill switch. Daily quotas allow **5 admitted requests per IP and 100 globally per UTC day**. Separate atomic attempt controls (20/IP and 1,000 globally per fixed ten minutes) protect body reading and verification. Malformed inputs and checkable mathematically invalid hands do not consume analysis quota. Busy requests are rejected before admission; admitted requests are not refunded. Redis failures block AI analysis.

The source defaults to `APPLICATION_ACCESS_MODE=private` for new environments. Explicit `public` mode enables access without application Basic Authentication while retaining request validation, usage controls and security headers. Private deployments require a configured access secret. Pages use a fresh CSP script nonce and dynamic rendering; security headers also cover API errors and static assets.

Implementation and operating details: [quota accounting](docs/ai-quota-accounting.md), [cost controls](docs/ai-cost-controls.md), [public access configuration](docs/public-launch.md), [security boundaries](docs/security-hardening.md) and [staging validation procedures](docs/staging-readiness.md). Earlier task-based notes describe historical source snapshots; the production release notes describe the published configuration.

### Server mathematical verification

The AI API replays pot, stack and action arithmetic from validated inputs and independently enumerates equity within a bounded server budget. Client simulations are never authoritative; expensive or interrupted equity calculations are explicitly unknown, and dependent Call EV is withheld. The AI review displays the returned server facts. See [the mathematical trust boundary, computation limits and compatibility notes](docs/mathematical-verification.md).

### AI request protection

The AI endpoint requires `Content-Type: application/json` (including valid parameters such as `charset=utf-8`). Unsupported media types return 415. Untrusted or malformed origins and unsafe Fetch Metadata return 403 before the body is read, Redis quota is consumed, or the AI provider is called. Misconfigured trusted origins fail closed with 503.

Origins must match the framework request URL or an exact entry in the optional server-side `AI_TRUSTED_ORIGINS` setting. Cross-site Fetch Metadata is rejected even for an allowlisted origin. No CORS permission is granted. A trusted origin entry does not enable a separate cross-origin browser frontend.

Direct deployments, including Vercel, use the request URL origin. If a reverse proxy presents an internal URL to Next.js, configure its external HTTP(S) origin explicitly, for example `AI_TRUSTED_ORIGINS=https://poker.example.com`. Multiple entries are comma-separated (maximum 16). Do not use paths, trailing slashes, credentials, wildcard subdomains, or an unrestricted `*.vercel.app` pattern. Add only aliases you control; remove retired preview origins. Invalid entries disable AI requests until corrected.

For local development, Next.js normalizes loopback addresses to `localhost`. Use the matching `http://localhost:<port>` URL, or explicitly add the exact `http://127.0.0.1:<port>` origin to `AI_TRUSTED_ORIGINS` when accessing the app through that address. Different ports are different origins.

Request-origin validation does not derive trust from `Host`, `Forwarded`, or `X-Forwarded-*` headers. The hosting platform or trusted ingress must construct the framework request URL safely, replace untrusted forwarding headers, and preserve `Origin`, Fetch Metadata, and `Content-Type`. An allowlist cannot repair an incorrectly configured proxy trust boundary.

Same-origin browser requests may omit `Origin`. Non-browser clients may omit both `Origin` and Fetch Metadata, but must still send JSON and pass the configured access policy (including Basic Authentication in private mode). This fallback relies on JSON being a non-safelisted browser media type and on CORS remaining disabled; Basic credentials alone never bypass the header checks. Requests identifying themselves as same-site need an explicit allowed origin. Navigation, `no-cors`, incomplete Fetch Metadata, and ambiguous header values are rejected.

## Technical architecture

~~~mermaid
flowchart LR
    Browser[Browser UI<br/>Next.js and React] --> Math[Poker engine<br/>hand evaluation, ranges, equity, pot odds, EV]
    Browser -->|User-requested review| Gate[Server access gate]
    Gate --> Validate[Input validation]
    Validate --> Replay[Action and deterministic math replay]
    Replay --> Limit[Shared usage controls]
    Limit --> Equity[Bounded server equity verification]
    Equity --> Provider[Server-side AI provider]
    Provider --> Schema[Structured response validation]
    Schema --> Browser
    Limit --> Redis[(Upstash Redis)]
    Provider --> OpenAI[OpenAI Responses API]
~~~

The browser handles hand entry and local mathematical previews. The server applies the configured access policy, validates request origin and inputs, independently verifies mathematical facts, protects provider credentials, enforces shared usage controls, and validates the structured response before returning it to the UI.

## Engineering highlights

- **Poker logic is separated from presentation:** hand evaluation, range generation, blockers, equity, call calculations, and action-state replay live in dedicated modules.
- **Range combinatorics are card-based:** range classes expand into legal physical combinations; Hero and board cards remove blocked combinations.
- **Responsive equity work:** exact enumeration is preferred within a bounded case space; chunked Monte Carlo is used for larger calculations.
- **Action-state validation:** action history, stacks, all-ins, effective stack, and SPR are represented and checked before AI review.
- **Strict AI response handling:** the provider response must be complete and match the expected structured fields before rendering.
- **Safe server boundaries:** AI and Redis credentials stay server-side. Production AI analysis uses shared rate limiting and fails closed if that control is unavailable.
- **Testable provider integration:** automated tests use a mocked provider and do not require paid API calls.

The public demo uses no-login access with IP-based usage controls. The same code supports Basic Authentication for private environments. Origin checks and shared quotas reduce abuse but do not establish a durable user identity.

## Privacy and usage boundaries

Local mathematical previews run in the browser. An explicit AI-review request sends the supplied hand, board, ranges, actions, stack assumptions and opponent context through the server to OpenAI. Do not include personal identifiers or confidential hand data. The application adds no accounts, analytics or persistent hand-history storage; browser localStorage stores the language preference. Redis stores expiring rate counters keyed by an HMAC-derived IP identifier and UTC day, not hand histories. Hosting and service providers may retain operational metadata under their own policies. Existing Google Fonts requests remain an external browser dependency.

Production AI review uses **5 validated admissions per IP per UTC day and 100 globally per UTC day**, with Redis failure blocking analysis. The Vercel policy requires one normalized platform client IP without an arbitrary forwarding-header fallback; see [trust assumptions and validation](docs/trusted-client-ip.md). Shared IPs share a quota; origin checks are not bot authentication. See [deployment security boundaries](docs/security-hardening.md).

## Getting started

### Requirements

- Node.js 22 (the CI runtime)
- npm

### Install and run

~~~bash
npm ci
cp .env.example .env.local
~~~

The example starts in private mode with AI disabled. Set a random `DEPLOYMENT_ACCESS_SECRET` before starting. Mathematical features work without an OpenAI key. To enable real AI reviews locally, configure `OPENAI_API_KEY` and `OPENAI_MODEL`, set `AI_CLIENT_IP_POLICY=local` for `npm run dev`, and set `AI_ANALYSIS_DISABLED=false`; provider requests incur API costs. Keep credentials in the untracked `.env.local` file and never use a `NEXT_PUBLIC_` prefix for secrets.

~~~bash
npm run dev
~~~

Open [http://localhost:3000](http://localhost:3000). At the local access prompt, use access as the username and the configured secret as the password.

### Environment variables

| Variable | Required for | Description |
| --- | --- | --- |
| OPENAI_API_KEY | AI review | Server-side credential for the OpenAI Responses API. |
| OPENAI_MODEL | Optional | Server-side model selection; defaults to `gpt-5.6-terra`. |
| AI_ANALYSIS_DISABLED | AI operating policy | `true` rejects AI requests before provider calls; the template sets `true` (AI disabled). Set `false` intentionally to enable reviews. |
| AI_MAX_OUTPUT_TOKENS | Optional | Default output cap: 16,000 tokens, including reasoning tokens. |
| AI_MAX_CONCURRENT_REQUESTS | Optional | Default shared AI concurrency limit: 3. |
| UPSTASH_REDIS_REST_URL | Production AI review | Shared Redis REST endpoint used by production usage controls. |
| UPSTASH_REDIS_REST_TOKEN | Production AI review | Server-side credential for the shared Redis limiter. |
| AI_CLIENT_IP_POLICY | Vercel AI review | Exactly `vercel`; requires exposed platform runtime markers and verified managed ingress. Local dev/test may leave unset or use `local`. |
| AI_TRUSTED_ORIGINS | Optional | Exact additional external origins for a trusted reverse proxy; comma-separated, without wildcards. |
| APPLICATION_ACCESS_MODE | Access policy | Unset/private requires Basic; explicit public enables no-login access. Invalid values fail closed. |
| DEPLOYMENT_ACCESS_SECRET | Private app access | Server-side secret required by the temporary access gate. |

The example environment file contains placeholders only. Configure production values in the hosting provider’s server-side environment settings. Never commit .env.local or expose credentials in browser code, screenshots, logs, or support material.

Tests use Node’s built-in test runner. They cover hand rankings and equity, ties and edge cases, ranges and blockers, action and stack state, request validation, language handling, structured response validation, and rate limiting. AI provider calls are mocked.

### Deployment

The live application is deployed on Vercel from `main`. Its Production environment explicitly configures public access, enabled AI and the Vercel IP policy. Credentials are stored only in Vercel; they are not in this repository. See the [production release and operating notes](docs/production-release.md).

For a separate deployment:

1. Import the repository as a Next.js project using Node.js 22.
2. Configure the access policy and environment-specific server secrets; use a separate Redis database for isolated testing.
3. Keep AI disabled while configuring and reviewing the deployment. For Vercel AI review, set `AI_CLIENT_IP_POLICY=vercel` and ensure platform system environment variables are exposed.
4. Deploy, review the application and intentionally enable AI only when the provider credentials and usage controls are ready.

Environment changes require a new deployment. The application kill switch does not stop provider requests already in flight or alter older immutable deployments.

## Limitations and roadmap

### Current limitations

- AI commentary can be incomplete or inaccurate. It is not solver output or guaranteed advice.
- Auto opponent ranges are qualitative assumptions, not exact probability distributions.
- Arbitrary per-combination range weights are not supported.
- Monte Carlo results are estimates and can vary between runs.
- The mathematical model does not cover multiway pots, rake, tournament ICM, or future betting trees.
- IP-based usage controls do not provide durable user accounts or per-user quotas; people behind the same public IP share an allowance.

### Possible next steps

- Improve abuse controls and usage visibility as the public demo gains traffic.
- Support weighted ranges and more game formats.
- Extend the mathematical model with rake, multiway pots, and tournament ICM.
