# Trusted client IP boundary (local Task 11 source)

Not deployed or live-verified. IP quotas identify a network address, not a person.

## Production/preview policy

Set the server-only `AI_CLIENT_IP_POLICY=vercel` intentionally for a deployment served exclusively through Vercel's managed ingress. Enable **Automatically expose System Environment Variables** in Vercel project settings; runtime must have `VERCEL=1` and `VERCEL_ENV=production` or `preview`. Unset, malformed or unsupported policy/runtime markers fail closed with the existing localized rate-limiter-unavailable HTTP 503. Self-hosted `next start` intentionally cannot enable AI merely by supplying forwarding headers. Custom Vercel environments are unsupported until explicitly reviewed.

The only accepted source is **one bare `x-vercel-forwarded-for` IP**. Missing, invalid, duplicate/list values fail closed before quota EVAL or OpenAI. Never choose a chain's first/last member or fall back to `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, `CF-Connecting-IP`, request host or `x-vercel-id`. Conflicting alternative headers are ignored, not used to choose an identity. Reject ports, brackets, IPv6 zone IDs, hostnames, legacy IPv4 spellings and comma-separated chains. Node's IP validator plus WHATWG IPv6 serialization canonicalize case/compression; IPv4-mapped IPv6 uses the same bucket as its IPv4 equivalent. HTTP Headers may trim surrounding HTTP whitespace before validation; it cannot create a second bucket.

[Vercel's request-header documentation](https://vercel.com/docs/headers/request-headers) describes replacement of ordinary forwarded-for values to prevent spoofing and the platform-specific header, including proxy caveats. [System variables](https://vercel.com/docs/environment-variables/system-environment-variables) identify the configured runtime. These variables are **deployment assertions, not cryptographic request authentication**. Application code cannot prove that a synthetic or directly delivered request passed through Vercel. This policy is safe only when every path to the function goes through the documented Vercel ingress, that ingress replaces client-supplied platform headers, and application middleware/rewrites do not replace them afterward. Do not manually fabricate Vercel markers on a directly reachable Node server. Header names alone establish no trust; `x-vercel-signature` for webhooks is not a general browser-request signature.

Assume direct client → Vercel → function, with no external reverse proxy or Enterprise Trusted Proxy configuration. A proxy in front may make its own network address the observed client; do not recover the visitor using an unverified external header. Multi-hop/custom proxy architecture requires its own reviewed authenticated boundary. Live topology and header replacement have not been inspected here. If staging cannot establish replacement and exclusive ingress, keep AI disabled. Minimal safe alternatives: use direct Vercel ingress, or restrict an origin to an authenticated trusted gateway that strips all incoming identity headers and emits a verified identity. Never enable arbitrary forwarding fallbacks.

## Accounting, local operation and privacy

Validated quotas now use the separate Redis-clock daily hash script; attempt Lua remains unchanged: **5 admitted validated requests per normalized IP per UTC day**, **100 globally per UTC day**. Canonical addresses are HMAC-hashed using the existing server Redis credential before Redis key construction. No raw IP logging or browser disclosure is added. Task 12 now checks identity at atomic attempt admission before body reading or concurrency acquisition; rejected identity increments no counter and calls no OpenAI. Concurrency acquisition still precedes analysis admission. See [attempt/admission semantics](ai-quota-accounting.md). Cancellation, release ownership, shutdown and all request security controls remain intact.

Only `NODE_ENV=development` or `test`, with **both Vercel markers absent**, and policy unset or exactly `local`, uses a single bounded process-local development bucket. It ignores every IP header, including missing headers, so spoofing cannot multiply local buckets. This is a convenience for a localhost server, not a public development server or global quota. Never deploy with these local conditions. Automated handler/provider unit tests inject an explicit test limiter; dedicated integration tests exercise the real Redis/IP path. Production never imports test support.

Normalization changes old noncanonical IPv6 bucket identities during rollout. Drain mixed-version instances or wait one ten-minute window before relying on uninterrupted IP accounting. No persisted data migration or refunds. Global counter names/accounting remain unchanged. Token rotation also changes HMAC bucket identities as before.

## Staging verification before release (manual; no deployment performed)

1. Use a protected staging Vercel deployment with separate Redis and a stubbed AI provider. Do not use paid calls to test ingress. Configure the policy and platform system variables; retain both Basic gates. Confirm production-build middleware preserves the platform header. Confirm no alternate direct origin exposes the function.
2. On both the deployment URL and custom domain, use one client connection/network and send requests with absent and fabricated `x-vercel-forwarded-for`, alternate XFF/X-Real-IP/Forwarded/CF headers, duplicate headers and comma chains. Using temporary protected, redacted instrumentation in staging only, establish that the function sees the **same normalized actual connection IP**, not supplied values. Do not publish an IP echo endpoint or log raw IPs/credentials/hand data. Browser code alone cannot send all forbidden headers; use an HTTP client for these tests.
3. Send five valid fixture requests then a sixth with changed spoofed headers. Expect five admissions and IP 429 on the sixth, one HMAC bucket and global count five. Repeat across two networks and IPv4/IPv6 where available, accounting for NAT and privacy address changes. Use stub provider/concurrency release and isolated Redis state. Confirm missing/malformed *server-visible* identity and invalid policy return 503, no quota EVAL/provider and released leases (unit tests cover these, platform normally supplies identity).
4. Repeat with any configured proxy, rewrite or middleware and verify which peer the platform reports. If chains or client-controlled identity survive, **stop launch** and correct topology instead of selecting a convenient chain element. Confirm Trusted Proxy settings with Vercel support if applicable; this implementation does not support that configuration.
5. Verify rolling deployments, previews, cancellation, Redis outages and quota boundaries. Remove temporary staging instrumentation. Do not change production values until separately authorized.

## Remaining risks

Actual Vercel header overwrite, topology and system-variable availability require staging verification. IP rotation, VPNs, IPv6 privacy addresses, botnets and NAT remain limitations; no IPv6 subnet aggregation is introduced because that changes quota semantics. Bots can exhaust the daily quota. Invalid traffic still consumes HTTP, validation and potentially concurrency Redis operations. Upstream body buffering and cancellation propagation remain platform risks documented in previous tasks. This change does not claim transport-level DoS protection, user identity or bounded infrastructure billing.
