# AI API mathematical trust boundary

The server verifies arithmetic **conditional on user-supplied primitive assumptions**. It cannot establish that the described hand happened, that cards or starting stacks were reported honestly, or that an opponent really plays the selected range. It does not certify solver/GTO output.

## Request and processing contract

Requests now require `blinds: { smallBlindBb, bigBlindBb }`. Both values are finite, nonnegative, bounded by the existing 1,000,000 BB input limit, and small blind cannot exceed big blind. The UI submits its existing blind settings. Old clients without this field must reload/update; the API rejects them instead of guessing the blinds.

Processing order:

1. Existing middleware/API Basic Authentication, header-only cross-origin/JSON protection, shutdown and atomic attempt protection (20/IP and 1,000 globally per fixed ten minutes).
2. Existing 32 KiB body cap and strict shape, card, range and numeric validation.
3. Replay of deterministic facts from primitive assumptions; reject contradictions with HTTP 400.
4. Existing global concurrency lease and bounded equity verification; reject contradictory results that can be checked exactly, or explicitly mark equity unknown.
5. Shutdown recheck, prompt construction and atomic shared Redis analysis admission (5/IP/UTC day and 100/UTC day).
6. Existing provider call and 60-second timeout, with only reconstructed facts. The structured response's mathematical summary is generated by the server. A separate `verifiedMath` response object supplies the review's displayed equity, EV and final pot.

Malformed, deterministic and checkable equity contradictions consume attempt capacity, never analysis quota. Attempts and concurrency protect verification before analysis admission; see [exact accounting and cancellation semantics](ai-quota-accounting.md). Unknown equity does not prevent a qualitative AI review. No CORS permission or additional authentication bypass is introduced.

## Field inventory

| Fields | Server treatment |
|---|---|
| Hero/Villain cards, board | Validate syntax, Hold'em lengths and physical uniqueness; user assumptions, not independently observed cards. |
| Positions, starting stacks, blind sizes, action choices and bet/raise targets | Validate bounded primitives; replay under the existing two-player model. |
| Range classes | Validate legal unique labels, nonempty physical combos and blockers. Range choice and equal-combo weighting are assumptions. |
| `range.comboCount`, `range.percentage` | Recompute from existing range functions; only canonical server values reach the provider. |
| `actionHistory[].amountBb` | Call amounts must match the replayed incremental call; bets/raises are street-total targets within stack/legal minimum limits; check/fold/all-in must carry null. |
| `actionHistory[].resolution` | Recompute incremental contribution, street total and all-in classification. Reject supplied contradictions; fill omitted resolutions. |
| `pot.currentPotBb`, `villainBetBb`, `callAmountBb`, `finalPotBb` | Reconstruct from replay, including blinds, previous contributions, stack-capped calls and returned excess. |
| Player remaining stacks and `isAllIn` | Recompute blind/action deductions and unmatched-chip returns from starting stacks. |
| Starting/current effective stacks, street-start pot/effective stack | Recompute from replay. |
| `spr`, `streetStartSpr`, `facingAllIn`, `canFullCall` | Recompute, including null/no-active-call cases. |
| `mathematicalContext.requiredEquity` (pot odds) | Recompute with `calculateCallAnalysis` using the verified decision point. |
| Equity, complementary Villain equity, tie share, source, method, evaluated cases | Exact server enumeration where budget permits; otherwise no numeric fact is forwarded. |
| `mathematicalContext.callEV` | Recompute from server equity and verified pot/call; unknown if equity is unverified or no call exists. |
| Opponent profile/HUD statistics | Bounded user observations, explicitly assumptions; not verified poker math. |

Derived deterministic values must match within an absolute `1e-7` numerical tolerance; the provider receives the newly computed values, never the submitted approximations. Existing range-summary input rounding tolerance is retained, then canonicalized. Exact client equity also uses `1e-7` tolerance and must have the correct case count.

## Equity computation policy

The API uses the existing hand evaluator and hand/range equity functions. It does not run Monte Carlo or accept a client sample count as a server work instruction.

- Maximum **1,000 exact combo/runout cases** per admitted calculation.
- Known-hand river: 1 case; turn: 44; flop: 990. Preflop exceeds the limit.
- Custom ranges: equal weighting of each legal physical combination. Multiply legal combo count by 1, 44, 990 or 1,712,304 runouts, according to board length. Full river ranges fit (990 legal combos); wide earlier-street ranges do not.
- Calculations yield every 32 cases for one hand. Range calculations yield between combos after at least 32 cases; each multi-combo job admitted by this policy has at most 44 runouts per combo. A single-combo range uses the hand calculator.
- A **250 ms cooperative wall-clock deadline** and request-abort signal stop publication. Partial results are discarded. This is not a hard OS CPU preemption deadline; one small batch may finish before the next cancellation check.
- At most one equity verification runs in a process at a time. There is no wait queue. Concurrent attempts receive unknown equity. This limit is per process, not a distributed semaphore; Redis continues to bound overall accepted requests.

A client Monte Carlo result is **never certified**. Where exact enumeration is available, a difference over 10 percentage points in equity or tie share is rejected as a gross inconsistency. Smaller differences are not treated as equality: the client estimate is discarded and the exact server result is used. This tolerance is not a confidence interval and does not prove the client ran a simulation. Where exact verification exceeds budget, even a claimed exact result is discarded; detecting whether that discarded assertion was fabricated is not possible within the chosen budget.

Unknown results carry `verification-limit`, `verification-busy`, or `verification-timeout`, with no equity/EV number or invented sample count. Undefined Auto ranges remain `auto-range`. These server reasons are not accepted as client provenance. Polish and English summaries explain that unverified client values are unused. Local mathematical previews may still show client calculations; the completed AI review uses `verifiedMath` returned by the API.

## Action-model boundaries and compatibility

The API reuses `calculateActionState` and `suggestNextAction`. It enforces action order, street transitions, board availability, no actions after fold, stack limits, outstanding calls, minimum bet/raise sizes, all-in exceptions and supplied resolution arithmetic. Histories must be complete from the configured blinds under this model; partial, edited or inconsistent histories previously accepted by the API can now return 400.

This remains a two-player review model with dead blinds from untracked seats. There is no support for extra players' contributions, antes, straddles, rake, multiway side pots, tournament-specific rules or independently imported casino hand histories. Starting stacks/blinds must include the assumptions intended by this model. The position order is the existing engine's order, not a new separate rules engine.

A shared-engine correction counts the portion of a Villain raise that matches Hero's earlier contribution in the contestable pot. Only genuinely unmatched excess is returned when Hero cannot fully call. A Villain all-in call is not treated as a new bet facing Hero. This changes previously incorrect raise pot odds/EV; regressions check that projected final pots equal replayed pots after calls.

## Offline verification

Run `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, and `node scripts/benchmark-math.cjs`. The benchmark uses synthetic deals, two warmups and ten measured runs per case, including shape validation and action replay. It makes no OpenAI or Redis requests and reports wall time and observed event-loop timer gaps. Local measurements are not Vercel latency guarantees; cold starts, host load and Redis/provider latency are excluded.
